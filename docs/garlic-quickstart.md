# Garlic: быстрый старт, .yggg-сайты и как работает маршрутизация

## 1. Сборка и установка

```sh
# macOS / Linux
sh scripts/setup.sh build                                   # только собрать в ./bin
sudo -E PEERS="tls://host:port" SITE_ADDR=127.0.0.1:8080 sh scripts/setup.sh install
sudo sh scripts/setup.sh uninstall                          # конфиг с ключами остаётся
```

```powershell
# Windows (PowerShell, install/uninstall — от администратора; нужен wintun.dll рядом с exe)
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1 build
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1 install -Peers "tls://host:port" -SiteAddr "127.0.0.1:8080"
```

`install` собирает проект, ставит бинарники, создаёт конфиг (`/etc/yggdrasil.conf`,
на Windows `%ProgramData%\Yggdrasil\yggdrasil.conf`) через `-genconf`, включает
`Garlic.Enabled`, опционально прописывает пиры и сайт, регистрирует сервис
(launchd / systemd / Windows service) и запускает его. Существующий конфиг и ключи
не перезаписываются. Нужен Go >= 1.26.

## 2. Как поднять свой .yggg сайт

1. Запусти обычный HTTP-сервер на loopback, например
   `python3 -m http.server 8080 --bind 127.0.0.1`.
2. В конфиге (блок `Garlic`) оставь сгенерированные ключи и задай:
   ```hjson
   Enabled: true
   Services: [ { ServiceID: "", LocalAddr: "127.0.0.1:8080" } ]
   ```
   (или передай `SITE_ADDR=127.0.0.1:8080` в установочный скрипт). Для HTTPS-бэкенда
   добавь `TLSLocalAddr`.
3. Запусти/перезапусти yggdrasil. Узнай адрес:
   ```sh
   yggdrasilctl getGarlicDomain       # <хеш>.domains.yggg
   yggdrasilctl getGarlicServices     # статус публикации и последняя ошибка
   ```
   В логе появится `Garlic website published`. Регистрировать имя не нужно:
   адрес — производная от твоего Ed25519-ключа `Garlic.SigningPrivateKey`.
   **Сохрани конфиг** — потеряешь ключ, потеряешь домен.
4. Чтобы открыть сайт с другой машины, на ней тоже включи `Garlic.Enabled` (прокси
   `127.0.0.1:4444` стартует по умолчанию) и либо укажи в браузере PAC
   `http://127.0.0.1:4444/proxy.pac`, либо HTTP-прокси `127.0.0.1:4444`.
   Открывай `http://<хеш>.domains.yggg/` (именно `http://`). Проверка:
   `curl --proxy http://127.0.0.1:4444 http://<хеш>.domains.yggg/`.

Читаемые имена вида `name.yggg` пока не реализованы — только хеш-адреса.
Подробности: [garlic-sites.md](garlic-sites.md), [garlic-domains.md](garlic-domains.md).

## 3. Нужно ли вписывать доверенные пиры? Как работает маршрутизация

**Коротко:** Garlic — это слой поверх Yggdrasil, а не отдельная сеть как Tor или I2P.
Поэтому «запустил и работает» верно только наполовину:

| Уровень | Нужно настраивать? |
|---|---|
| Транспорт Yggdrasil (mesh) | **Да.** Нужен хотя бы один пир в `Peers` (публичный узел) — или другая машина в той же LAN: multicast найдёт её сам. В Yggdrasil нет встроенного списка bootstrap-узлов. |
| Обнаружение Garlic-узлов (кандидаты в цепочки) | **Нет, автоматически.** |
| Поиск сайтов (каталог дескрипторов) | **Нет, автоматически.** |

### Обнаружение Garlic-узлов

- При старте узел спрашивает прямых mesh-пиров, поддерживают ли они Garlic
  (capability-запрос `garlic-v2`), и запоминает ответивших.
- Каждые ~30 с узел обменивается с несколькими проверенными соседями (gossip) выборкой
  известных Garlic-узлов (до 16) — так пул кандидатов растёт сам. Лимит пула —
  `MaxDiscoveredPeers` (1024). Не-Garlic узлы об этом не знают и ничего не видят.
- `Garlic.BootstrapPeers` (hex-ключи узлов) нужен **только** если твои прямые пиры
  сами не запускают Garlic: тогда нужен хотя бы один известный Garlic-узел как точка входа.
  Аналог `Peers`, но для Garlic.
- Узлы без Garlic просто не выбираются в цепочки, обычный Yggdrasil у них работает как раньше.

### Построение цепочек

Источник сам выбирает путь из `PathLength` (по умолчанию 3) Garlic-узлов, с учётом
минимального расстояния в mesh (`MinHopCount`, 2) и разнообразия префиксов/веток
дерева, чтобы хопы не принадлежали одному оператору. Пакеты послойно шифруются
(как в onion routing), каждый хоп знает только соседей; есть padding, jitter и
cover traffic. Цепочки ротируются (сайтовые — каждые ≤90 с).

### Как находится сайт (аналог hidden services)

1. Хост строит исходящую цепочку до relay-узла и регистрируется там (подпись привязана
   к этой цепочке). Подписанный дескриптор перечисляет relay, а не IP хоста.
2. Дескриптор публикуется в распределённый каталог: ключ — GID (хеш домена), хранят
   3 ближайших по XOR-расстоянию узла (как в Kademlia), запросы идут внутри цепочек.
   Дескриптор живёт ~3 минуты и автоматически обновляется.
3. Клиент итеративно ищет дескриптор (до 24 узлов), проверяет подпись и привязку к
   домену, строит свою цепочку к тому же relay. Relay склеивает две цепочки и пересылает
   непрозрачные QUIC-пакеты; сквозное шифрование и аутентификация — между клиентом и хостом.

### Отличия от Tor / I2P (честно)

- Нет directory authorities (Tor) и reseed-серверов (I2P): узлы находятся через mesh-пиров и gossip,
  а mesh-пиры всё равно надо один раз указать (или иметь в LAN).
- Нужны хотя бы 3 Garlic-узла с достаточной топологической разнесённостью: в крошечной сети
  цепочки не построятся (для тестов можно `PathLength: 1`, `MinHopCount: 0`, но приватности это не даёт).
- Сеть экспериментальная и малая: анонимность слабее, чем у Tor (см. [garlic-threat-model.md](garlic-threat-model.md)).
  Каталог хранится в памяти, репликация best-effort.
- Минимальный «просто работает» сценарий: прописать один публичный пир в `Peers` и включить
  `Garlic.Enabled`; если этот пир (или его соседи) не Garlic — добавить его ключ в `BootstrapPeers`.
