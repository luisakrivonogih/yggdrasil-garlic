# Garlic: быстрый старт, .yggg-сайты и модель безопасности

## 1. Две роли узла

| | `Mode: client` (по умолчанию, скрытый) | `Mode: relay` (публичный) |
|---|---|---|
| Для чего | ноутбук/десктоп, узел с сайтом | сервер с постоянным адресом |
| Отвечает на запросы Garlic | нет — выглядит как узел без Garlic | да, подписанным `RelayInfo` |
| Пересылает чужие цепочки | нет | да |
| Хранит каталог сайтов | нет | да |
| Хостинг сайтов | да (лучший вариант) | да, но время работы relay видно всем |
| Кто знает, что узел использует Garlic | только его доверенные пиры | все |

Это аналог hidden mode в I2P: скрытый узел никому не отвечает, и обойти сеть,
чтобы перечислить пользователей Garlic или найти хост сайта, нельзя.

## 2. Установка

```sh
# сервер (Linux): публичный relay
curl -fsSL https://raw.githubusercontent.com/luisakrivonogih/yggdrasil-go/develop/install.sh | sh

# свой компьютер (macOS/Linux): скрытый клиент, первый хоп — ваш сервер
sudo -E PEERS="tls://IP_СЕРВЕРА:ПОРТ" TRUSTED="<Public key сервера>" sh install.sh
```

```powershell
# Windows
powershell -ExecutionPolicy Bypass -File scripts\setup.ps1 install -Peers "tls://IP:ПОРТ" -Trusted "<Public key сервера>"
```

Переменные установщика: `PEERS` (обычные пиры Yggdrasil), `TRUSTED` (доверенные
Garlic-relay), `MODE` (`client`/`relay`), `SITE_ADDR` (локальный HTTP-сервер для сайта).
На Linux-сервере: `PEERS`, `GARLIC_TRUSTED_PEERS`, `GARLIC_MODE` (по умолчанию
остаётся прежний режим; `relay` при первой установке), `SITE_ADDR` (публикует сайт и
переводит узел в `client`: сайт держит только скрытый узел).
Скрипт сам делает `git pull`, переносит старый конфиг на новые поля и проверяет
итоговый конфиг перед перезапуском (при ошибке остаётся прежний).

**Переустановка ничего не сбрасывает:** ключи, `Peers`, `TrustedPeers` и режим
сохраняются, `PEERS`/`TRUSTED` только добавляются к спискам (`REPLACE_LISTS=1` —
заменить). Перед каждой установкой пакет кладёт копию конфига в
`/var/backups/yggdrasil.conf.<дата-время>`.

## 3. Доверенные пиры и первый хоп

Первый хоп **каждой** цепочки — всегда один из доверенных relay
(`Garlic.TrustedPeers`). Он видит ваш ключ узла, поэтому выбирать его должны вы,
а не случайность. Выбранный guard закрепляется и используется, пока работает.

Ключ доверенного пира — это **ключ узла Yggdrasil**, строка `Public key` из
`yggdrasilctl getSelf` на сервере (или поле `nodeKey` в `getGarlicIdentity`).
Это не Garlic-ключ: onion-ключи ротируются и в конфиг не пишутся.

```sh
yggdrasilctl addGarlicPeer key=<ключ узла>     # проверяет, добавляет и сохраняет в конфиг
yggdrasilctl removeGarlicPeer key=<ключ узла>  # убирает и из конфига
yggdrasilctl getGarlicPeers                     # доверенные, текущий guard, известные relay
```

`addGarlicPeer`/`removeGarlicPeer`, как и `addPeer`/`removePeer`, сразу записывают
изменение в файл конфига, с которым запущен демон (`saved: true` в ответе). То же
самое вручную:
```hjson
Garlic: {
  Enabled: true
  Mode: client
  TrustedPeers: [ "<ключ узла relay>" ]
}
```

Доверенный relay должен быть достижим по mesh: укажите его в обычных `Peers`
(или любой путь до него). `TrustOutboundPeers: true` дополнительно делает
доверенными все ваши исходящие `Peers` (кроме LAN/multicast и входящих).

Без доверенных пиров цепочки не строятся — это намеренно.

## 4. Как строится цепочка

1. **Первый хоп** — доверенный relay (guard). Только ему узел пишет напрямую.
2. **Остальные хопы** берутся только из локально известных подписанных `RelayInfo`
   (получены через gossip от доверенных пиров, из ответов каталога или из
   дескриптора сайта). Узел **никогда не обращается к ним напрямую** — иначе
   промежуточный хоп узнал бы, кто сейчас построит через него цепочку.
3. `RelayInfo` подписан ключом узла relay, поэтому пересказавший его сосед не может
   подменить onion-ключ (только утаить relay).
4. Guard никогда не бывает последним хопом той же цепочки.

## 5. Ротация ключей и прямая секретность

- Onion-ключ relay (X25519) генерируется в памяти, на диск не пишется и меняется
  каждые `OnionKeyRotation` (по умолчанию 1 ч). Старый ключ живёт ещё ~1 ч
  (переходный период), затем затирается нулями.
- После удаления ключа записанный ранее трафик через этот relay расшифровать нельзя,
  даже получив полный доступ к серверу. Окно прямой секретности ≈ 2 часа.
- Сам контент сайтов дополнительно защищён сквозным TLS 1.3 (своя прямая секретность).
- `Garlic.PrivateKey` больше не используется. Постоянным остаётся только
  `SigningPrivateKey` — из него получается адрес сайта.

## 6. Как поднять .yggg сайт

Сайт может держать **любой** узел: достаточно поправить его конфиг. Сайтов на узле
может быть несколько.

1. Запустите веб-сервер на loopback, например `python3 -m http.server 8090 --bind 127.0.0.1`
   (порт 8080 занят дашбордом, если он включён).
2. В секции `Garlic` конфига перечислите сайты:
   ```hjson
   Services: [
     { Name: "blog", ServiceID: "", LocalAddr: "127.0.0.1:8090" }
     { Name: "shop", ServiceID: "", LocalAddr: "127.0.0.1:8091" }
   ]
   ```
   (или при установке: `SITE_ADDR=127.0.0.1:8090 SITE_NAME=blog`; режим узла не меняется).
3. Перезапустите Yggdrasil и проверьте:
   ```sh
   yggdrasilctl getGarlicServices            # домены, "published": true или последняя ошибка
   yggdrasilctl getGarlicDomain name=blog    # домен сайта, не публикуя его
   ```
4. Открыть сайт: на любом узле с Garlic в браузере укажите прокси `127.0.0.1:4444`
   (или PAC `http://127.0.0.1:4444/proxy.pac`) и откройте `http://<хеш>.domains.yggg/`.
   Проверка: `curl --proxy http://127.0.0.1:4444 http://<хеш>.domains.yggg/`.

**Почему по сайту нельзя найти узел и связать сайты между собой.**
- У каждого сайта свой ключ подписи, выведенный из `SigningPrivateKey` и `Name`
  (HKDF). Дескриптор, TLS-сертификат и регистрация на relay содержат только этот
  ключ, так что по криптографии два сайта одного узла выглядят как сайты разных
  узлов, а с узлом не связаны вовсе. Домен сайта постоянен, пока не меняются
  `SigningPrivateKey` и `Name`. Сайт без `Name` — домен узла по умолчанию.
- Хост выходит в сеть только через свой guard и цепочки. Relay сайта видит лишь
  предыдущий хоп, каталог — только цепочки. Каждый сайт выбирает свой relay и
  строит свои цепочки; хост никогда не берёт guard в relay своего сайта.
- Сайты публикуются в случайные моменты, независимо друг от друга, а сертификаты
  не содержат времени запуска, поэтому одновременный старт сайтов не выдаёт.
- **`SigningPrivateKey` держите в секрете:** по нему связываются все ваши сайты.

**Что остаётся** (как и в Tor/I2P): сайты одного узла включаются и выключаются
вместе, и наблюдатель, долго следящий за доступностью, может это сопоставить. У
relay время работы видно всем (он отвечает на запросы Garlic), поэтому самая
сильная защита — держать сайты на скрытом узле (`Mode: client`). На relay сайты
тоже работают; узел при запуске пишет об этом предупреждение.

Минимальная сеть для сайта с `PathLength: 3`: три relay. Хост и клиент
используют guard, один промежуточный relay и relay сайта.

Промежуточный relay должен быть не ближе `MinHopCount` (по умолчанию 2) переходов
по сети Yggdrasil от узла. Поэтому relay, с которыми узел соединён напрямую
(`Peers`), промежуточными быть не могут. Если хост или клиент напрямую соединён со
всеми relay, цепочка не строится и сайт не публикуется. Подключайте скрытый узел
только к его guard или задайте на нём `Garlic.MinHopCount: 1` (разумно, когда все
relay ваши).

### Если сайт не открывается

| Ошибка на клиенте | Что значит |
|---|---|
| `GID not found: N directory relay(s) answered but none has it` | каталог доступен, но сайт не опубликован: смотрите `getGarlicServices` на хосте |
| `no reachable distributed directory peers: no Garlic relays known yet` | клиент ещё не узнал relay от доверенных пиров: подождите минуту, проверьте `getGarlicPeers` |
| `... not enough topologically diverse candidates: ... closer ...` | все relay соединены с узлом напрямую: см. абзац выше про `MinHopCount` |
| `no trusted Garlic peers configured` | не задан `TrustedPeers` (или `addGarlicPeer` потерялся после перезапуска) |

`addPeer` и `addGarlicPeer` сохраняются в конфиг. Если в ответе `saved: false`,
причина в `saveError` (например, конфиг недоступен для записи) — тогда пир действует
только до перезапуска.

## 7. Что видит каждый участник

| Участник | Что знает |
|---|---|
| Ваш прямой пир Yggdrasil | ваш IP и что вы обмениваетесь трафиком с guard |
| Guard (доверенный) | ваш ключ узла и что вы пользуетесь Garlic; не знает, какие сайты |
| Промежуточный relay | только соседние хопы |
| Relay сайта | GID сайта и предыдущий хоп; не знает ни хост, ни клиента |
| Каталог | какие GID ищут и публикуют; не знает, кто |
| Остальная сеть | ничего: скрытые узлы не отвечают на запросы Garlic |

Ограничения: сеть маленькая (анонимность слабее, чем у Tor); злонамеренный доверенный
пир может утаить часть relay (eclipse) — поэтому доверенными делайте только свои
или проверенные узлы; корреляция трафика на входе и выходе остаётся возможной,
если обоими владеет один противник. Подробнее: [garlic-threat-model.md](garlic-threat-model.md).

## 8. Отличия от Tor и I2P

| | Tor | I2P | Garlic |
|---|---|---|---|
| Откуда узнаёт сеть | зашитые directory authorities | reseed-серверы | доверенные relay (вы указываете) + gossip |
| Видны ли пользователи | нет | да (кроме hidden mode) | нет (client по умолчанию) |
| Первый хоп | guard на месяцы, случайный | профили пиров | guard из ваших доверенных, закреплён |
| Связь ключей relay | подписанный дескриптор | RouterInfo в netDb | подписанный `RelayInfo` |
| Ротация onion-ключей | да (недели) | редко | да (1 ч, старый стирается) |
